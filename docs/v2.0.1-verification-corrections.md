# 2.0.1: 过程内验证与知识纠错

日期: 2026-09-20. 状态: 2.0.1 实现及本轮验收完成; 用户已授权同步云端仓库. 下列测试证据保留验收时身份, 云端执行状态以对应提交的 CI 为准; 本机安装另计.

用户在第二轮证明审计后提出两项目标: 增强检验 agent 并把形式化融入研究过程; 建立能够接收内部或外部错误报告、修订工具库并阻止错误继续传播的模块. 检验必须由不继承作者上下文的无状态隔离子 agent 完成. 本次保留 2.0 的自由探索方向, 将必要约束集中在结论采信和知识复用上.

## 目标一: 让每个承重步骤有对应证据

研究者可以选择证明路线和拆分粒度. 对定义、成员关系、边界条件、量词变化、归一化和依赖连接等承重接口, 明确实际假设及待证结论, 在开发过程中使用 Lean 的目标和编译反馈. 对尚无形式化的分析步骤保留可审查解析证明或精确缺口. 数值实验、精确有限计算、解析证明、局部 Lean 证明与根定理形式化分别记录.

验证分工围绕具体证据进行:

| 角色 | 可见材料 | 产出及权限 |
| --- | --- | --- |
| 研究/修订作者 | 原问题、文献、试验、既有经验 | 修改候选证明、修订卡片、使用 Lean 反馈, 不自发独立验收 |
| 形式陈述回译者 | 冻结的实际 Lean 声明、定义和环境 | 新会话逐项回译量词、隐含前提与边界; 不看作者想证明什么 |
| 数学/语义检验者 | 精确目标、证明、必要来源、机器证据; 形式化时加回译 | 新会话核对推导和含义, 给出范围明确的判决; 不改其审批对象 |
| 协调器及确定性工具 | 真实调度/完成回执和文件身份 | 保存证据、拒绝陈旧结果、安排修订; 不将流程成功当成证明 |

同一 agent 的改名不构成独立性. Codex 调度显式使用 `fork_context:false`. 每次修订后的重新验收启动新 verifier; 作者自测可以持续使用缓存和开发会话. 如独立检验或 Lean 不可用, 对应状态保持未完成, 其它研究工作可以继续.

方法依据: Fuse 的公开 agent 实现提供可复用编译反馈与局部证明任务, Prove2Me 的公开规范要求回译者使用新上下文且只看形式陈述. 本次重新读取了固定版本的一手说明. [Numina agent](https://github.com/project-numina/numina-lean-agent/blob/1c9af8a52e715f22fede766425ba3d3b95526132/README.md), [Prove2Me 回译规范](https://github.com/prove2me/prove2me_workspace/blob/6b46503a65c3a4252170ed5ca984a796b5a5b6b4/references/mission_auditor.md). Lean 检查的是形式声明及其依赖; 原数学目标是否被忠实表达仍需核对. [Lean 验证说明](https://lean-lang.org/doc/reference/latest/ValidatingProofs/).

## 目标二: 纠错能够真正改变后续检索

错误报告保留为来源, 先核实其数学内容. 工具库以精确卡片版本登记问题, 暂停相关条目默认复用, 沿显式版本依赖标记下游待复核. 不明依赖还需额外检索正文、来源及人工链接; 依赖图不可能自动覆盖从未记录的关系.

修订替换活动内容, 保留原卡片、批注、失败路径与原审计. 恢复必须针对这次问题及具体修订版本完成独立复核. 重建指针、文件改名、补一个 `pass:true` 或修改状态文字均不能解除问题. 一个依赖被否定也不自动否定所有下游命题: 可能存在独立证明, 但需要重新核查相应路线.

实现入口:

- [检验包与原生工具回执](../plugins/manage-math-research-program/skills/manage-math-research-program/references/v2-review.md): `research_review.py`.
- [纠错生命周期与指针](../plugins/manage-math-research-program/skills/manage-math-research-program/references/v2-corrections.md): `research_corrections.py` 与库检索集成.
- [研究中的验证循环](../plugins/math-research-workflow/skills/math-research-workflow/references/v2-verification-loop.md): 短入口和按需细节.

检验工具检查真实回执的关联和一致性, 信任边界标为 `COORDINATOR_ATTESTED_TOOL_TRANSCRIPT`. 它不具备服务端签名鉴真能力, 也不是 OS 沙箱. 协调器必须保存实际工具返回, 不能编造完整回执. Blueprint canonical 仍由既有 reviewed receiver 管理, 纠错模块只提供复用屏蔽和待处理影响, 不越过 canonical 接收边界.

## 用本轮实际错误验收

| 场景 | 要求 |
| --- | --- |
| 谱基遗漏 x, 错用正弦范数 | 每个谱模态的非退化正对照先通过, 再解释等距检验 |
| x² 的截断和掩盖发散 | 域成员性先判定; 有限和不以完整范数命名 |
| 平衡配置被直接当作全局极值 | 分开候选值、全局界、达到性及引用依赖 |
| K1 正文与工具卡归一化不一致 | 卡片单独核对范围, 不继承正文的状态标签 |
| 外部报告针对某旧版工具 | 暂停复用、绑定旧版、登记修订、真实隔离复核后恢复 |
| 输入改动、重建索引、陈旧批准 | 旧回执失效, 问题保持可追踪且不会静默清除 |

真实数学检验曾发现 K1 卡片遗漏有限公式范围及极限归一化、高频积分失败、弱探针、比值摘要与递推算术错误;
修改前的 `CHANGES_REQUIRED` 和回译 `INCOMPLETE` 原样保留. 最后的谱域/K1、比值/MW 和局部 Lean 分别得到新隔离会话的有范围批准.

软件也经历了真实否决和修复: 日志末尾丢失漏检、格式损坏卡片的检索旁路、中断登记恢复、冲突路径别名,
以及上游单卡恢复误放行下游. 最后一项由新检验发现并在旧代码上复现失败;
现先保留完整的受影响依赖闭包, 再只对获得批准的具体版本解除问题. 直接与传递下游仍需各自修订、复核.
又一独立检验发现同路径多个依赖版本在输入字典中互相覆盖; 已在登记、旧记录读取及输入汇集时拒绝冲突,
同时测试依赖覆盖修订卡本体绑定的情况. 这类失败也保留原始否决.
当前软件已由另一新会话独立批准. 该检验执行所提供的 83 项测试及另写的 10 组独立测试,
并再次核对全部 14 个输入的哈希; 原生回执见
[最终软件批准](v2.0.1-evidence/independent-software-approved.json).
83 项不包括协调器另执行的 Q9 库复用测试, 因此与下述完整本机套件的 84 项不冲突.
真实成果仓库已按依赖顺序恢复九张修订卡, 并逐张查询确认当前版本可检索.
指针最终为 78 张可用、1 张隔离; 撤回卡只在显式历史查询出现, 92 个历史版本快照保持可核对,
新增三条版本绑定的纠错经验批注. 四个问题、11 个历史修订和九次恢复的原始事务均保留.
完整记录位于成果仓库 `reports/proof-audit-round2-20260920/REPORT.md` 和
`research/artifacts/proof-audit-round2-20260920/corrections/final-lifecycle.json`.

当前修订的行为测试在 Linux 和原生 Windows 各 **84 项通过** (40 项纠错、16 项库检索、16 项检验回执,
以及经验记录和兼容行为). 另有 **7 项库兼容检查、12 项 Lean 便携检查和 81 项仓库检查** 通过.
实际测试日志见 [证据目录](v2.0.1-evidence/). Windows 首轮因缺 PyYAML 有两项失败;
按文档依赖补到单独测试目录后通过, 未降低格式检查. 新的进程退出用例在两个平台运行,
但不覆盖断电持久性或所有并发交错. 单元测试的合成回执只验证软件行为, 不算真实独立审计.

回执当前还绑定调度时的绝对证据包路径. 本轮实测: 原生 Windows 能读取同一工具库并得到完全相同的九卡检验要求,
但无法直接消费从 WSL 路径调度的回执, 因为最小 prompt 路径不同; 记录为环境限制, 没有改写原始调度记录.
真实验收与恢复使用原 WSL 项目路径. 两平台各自的行为测试通过不等于证明跨路径搬迁后的回执可直接复用.
本机实际逐卡恢复约 48-82 秒, 尚未进行速度对照实验; 当前实现优先保证问题、版本、依赖与批准的一致性.

正确率提升仍需后续同题对照研究衡量. 本次功能修补和局部形式化不构成全仓库证明认证, 也不宣称能保证每一步数学推理永远正确.
